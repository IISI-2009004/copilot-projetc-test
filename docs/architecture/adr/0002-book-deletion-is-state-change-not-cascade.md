# ADR-0002: 書本刪除為單純狀態變更，不級聯刪除閱讀記錄

## Decision - 2026-07-31
**Decision**: `DELETE /api/books/{id}` 僅將該書本標記為 `deleted = true`（軟刪除）並移除其 Tag 映射，
**不會**刪除、修改或以任何方式觸碰該書本關聯的 `ReadingRecord`。既有閱讀記錄永久保留，
可持續被查詢（歷史、日曆、統計）。book 模組與 reading 模組之間**不再需要** ADR-0001 提出的
`BookDeletedEvent` 跨模組事件機制。

**Context**:
- ADR-0001 為解決「US-B04 要求刪書時同步刪除閱讀記錄」與「模組邊界禁止跨模組直接存取 Repository」
  之間的矛盾，設計了 `BookDeletedEvent` 事件通知機制。
- 使用者於審查中明確指出：「刪除書本並不會刪除閱讀紀錄，該書本可以不從 DB 刪除資料，而做資料狀態的變更」。
  這代表 US-B04 的原始描述（同步刪除閱讀記錄）本身就是不正確的需求，應予修正而非在架構上想辦法滿足它。

**Options**:
1. **維持 ADR-0001 的事件機制** — 與使用者明確表達的產品行為不符，予以否決。
2. **書本刪除僅為狀態變更，閱讀記錄不受影響** — 符合使用者指示，同時徹底消除了模組邊界衝突
   （因為根本不需要跨模組通知），是最簡單且風險最低的方案。

**Rationale**:
選項 2 不僅滿足使用者需求，也讓系統設計更簡潔：
- 閱讀記錄本質上是「使用者曾經花時間閱讀某本書」的歷史事實，不應因書本被下架/刪除而抹除，
  這在資料語意上更合理（類似訂單刪除商品後，歷史訂單紀錄仍保留商品名稱快照的概念）。
- book 與 reading 模組間恢復為單一方向依賴（reading → book 的 `BookQueryPort` 查詢），
  不需要事件發布/監聽的額外複雜度與交易一致性考量，降低實作與測試成本。
- `BookQueryPort.existsBook()` 已經隱含「刪除後無法再新增該書的閱讀記錄」的保護，
  足以避免對已刪除書本產生新的資料寫入，無需額外的級聯刪除邏輯。

**Impact**:
- `requirements.md` US-B04 修正為狀態變更語意，移除 US-R06（事件監聽刪除記錄）。
- `design.md` 移除 §5b（BookDeletedEvent 契約）、移除刪除書本的事件序列圖，
  package 結構移除 `book/event`、`reading/listener`。
- `tasks.md` 移除 A6（發布事件）、B6（監聽事件）任務；A2/B5 補充「刪除書本不影響閱讀記錄」的測試案例。
- `docs/security/threat-model.md` 移除跨模組事件相關的 Repudiation/濫用風險項目。
- ADR-0001 標記為 Superseded，保留作為決策歷程與未來對照（例如將來若真的需要「刪除書本時清理相關資料」
  的需求，可參考該事件機制的設計）。

**Review**:
若未來產品需求變更為「使用者可選擇是否在刪除書本時一併清除閱讀記錄」（例如加上確認勾選框），
屆時應重新評估是否需要類似 ADR-0001 的事件機制，或改為 Service 層顯式呼叫（但仍須遵守模組邊界規則，
不可讓 book 直接存取 reading 的 Repository）。
