## 2. User Story

### 📝 範本

> **As a** {角色/使用者}，
> **I want** {想要達成的目標/功能}，
> **So that** {達成後帶來的價值/效益}。

### 💡 範例

> **As a** 公司員工，
> **I want** 能在系統上線上申請請假並即時查看核准狀態，
> **So that** 我不需要再透過紙本簽核，並能更快得知請假是否核准。

## 3. 功能需求（Functional Requirements）

### 📝 範本

依 MoSCoW 優先序列出所有功能需求：

| 需求編號 | 需求描述       | 優先序（Must/Should/Could/Won't） |
| -------- | -------------- | --------------------------------- |
| FR-001   | {功能需求描述} | Must                              |
| FR-002   | {功能需求描述} | Should                            |
| FR-003   | {功能需求描述} | Could                             |
| FR-004   | {功能需求描述} | Won't（本次不做）                 |

### 📖 使用說明

- **Must have**：沒有此功能，本次交付即失敗
- **Should have**：重要但非必要，可延後但應盡量納入
- **Could have**：有更好，資源允許時再做
- **Won't have（this time）**：明確排除在本次範圍外，避免範疇蔓延

### 💡 範例

| 需求編號 | 需求描述                                       | 優先序            |
| -------- | ---------------------------------------------- | ----------------- |
| FR-001   | 員工可於系統中選擇假別、起訖日期並送出請假申請 | Must              |
| FR-002   | 主管可於系統中核准或駁回請假申請並填寫意見     | Must              |
| FR-003   | 系統於申請送出後以 Email/App 通知主管          | Should            |
| FR-004   | 員工可查看歷史請假紀錄與剩餘假別天數           | Should            |
| FR-005   | 支援請假申請附件上傳（如證明文件）             | Could             |
| FR-006   | 支援跨部門代理人核准機制                       | Won't（本次不做） |

## 5. 驗收條件（Acceptance Criteria）

### 📝 範本

使用 Given-When-Then 格式撰寫，每個功能需求至少對應一組驗收條件：

```gherkin
Scenario: {情境名稱}
  Given {前置條件}
  When {使用者操作/事件}
  Then {預期結果}
```

### 💡 範例

```gherkin
Scenario: 員工成功送出請假申請
  Given 員工已登入系統且尚有可用特休天數
  When 員工選擇「特休」假別、填寫起訖日期並點選「送出」
  Then 系統應建立一筆狀態為「待核准」的請假申請
  And 系統應以 Email 通知該員工的直屬主管

Scenario: 請假天數超過剩餘天數
  Given 員工已登入系統且特休剩餘天數為 2 天
  When 員工申請 3 天特休並點選「送出」
  Then 系統應顯示錯誤訊息「剩餘天數不足」
  And 系統不應建立請假申請紀錄

Scenario: 主管核准請假申請
  Given 主管已登入系統且有一筆待核准的請假申請
  When 主管點選「核准」
  Then 該請假申請狀態應更新為「已核准」
  And 系統應以 Email/App 通知申請人核准結果
```

## 📖 使用說明

### 各章節填寫指引

| 章節          | 填寫時機          | 負責人      | 重點說明                              |
| ------------- | ----------------- | ----------- | ------------------------------------- |
| §1 文件資訊   | 文件建立時        | 需求分析師  | 確保版本與來源追蹤                    |
| §2 User Story | 需求訪談後        | PO/BA       | 遵循 As a / I want / So that 格式     |
| §3 功能需求   | 需求分析中        | BA          | 以 MoSCoW 排序，避免範疇蔓延          |
| §4 非功能需求 | 需求分析中        | BA/SA       | 需與架構師確認可行性                  |
| §5 驗收條件   | 需求定案前        | BA/QA       | Given-When-Then，需涵蓋正常與異常情境 |
| §6 安全考量   | 需求分析中        | BA/資安人員 | 對照 OWASP Top 10，標註資料分類       |
| §7 影響範圍   | 設計階段前        | SA          | 供架構師評估技術影響與工作量          |
| §8 追溯矩陣   | 設計/測試階段補充 | BA/QA       | 確保需求可追溯至測試案例              |

### 撰寫原則

1. **單一職責**：一個 User Story 只描述一個使用者目標，過大應拆分為多個 Story
2. **INVEST 原則**：Independent（獨立）、Negotiable（可協商）、Valuable（有價值）、Estimable（可估算）、Small（夠小）、Testable（可測試）
3. **驗收條件先行**：驗收條件應在開發前與 PO/QA 對齊，避免驗收爭議
4. **安全內建（Security by Design）**：安全考量應於需求階段即納入，而非留待測試階段才補強
