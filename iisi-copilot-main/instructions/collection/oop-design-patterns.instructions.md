# Design Patterns for Object-Oriented Programming for Clean Code 物件導向程式設計的設計模式，打造整潔程式碼

這些說明配置 GitHub Copilot，使其在生成或重構程式碼時優先考慮四人幫 (GoF) 設計模式、SOLID 原則和清晰的物件導向程式設計 (OOP) 實踐。

## Core Architectural Philosophy 核心架構理念

- **面向介面編程，而非面向實作：** 始終優先選擇抽象類別或接口，而非具體實作。使用依賴注入來提供具體實例。
- **偏好物件組合而非類繼承：** 使用組合在運行時動態組合行為。避免深層繼承樹。在適當的情況下使用委派來重用行為而不破壞封裝。
- **封裝變化的部分：** 識別應用程式中會變化的部分，並將其與保持不變的部分分離。使用策略模式、狀態模式或橋接模式來隔離這些變化。
- **鬆耦合：** 最小化類之間的直接依賴。使用中介者模式、觀察者模式或抽象工廠來保持組件的解耦。

## Creational Patterns Guidelines 創建型模式指南

在產生涉及物件建立或實例化的程式碼時，應用下列模式將系統與其物件的建立方式解耦：

- **Abstract Factory:** 當系統必須配置為多個相關產品家族之一時使用（例如，跨平台的 UI 元件）。確保客戶端僅與抽象工廠和抽象產品接口互動。
- **Factory Method:** 當類無法預測必須創建的物件類型時使用。將實例化延遲到子類。
- **Builder:** 當構建複雜物件需要逐步過程時使用，特別是當相同的構建過程可以產生不同的表示時。
- **Singleton:** 僅在絕對必要時使用，以保證類的單一實例並提供全局訪問點（例如，中央配置管理器或硬體接口）。在可能的情況下，優先使用依賴注入而非嚴格的單例模式。
- **Prototype:** 用於避免建立工廠的類層次結構，或當從頭創建物件比克隆現有物件更昂貴時使用。

## Structural Patterns Guidelines 結構型模式指南

在產生定義類和物件如何組合以形成更大結構的程式碼時，應用下列模式：

- **Adapter:** 用於使不兼容的接口能夠協同工作。優先使用物件適配器（使用組合）而非類適配器（使用多重繼承）以獲得更大的靈活性。
- **Bridge:** 用於將抽象與其實作分離，使兩者可以獨立變化（例如，將高階的 `Window` 概念與平台特定的 `WindowImpl` 邏輯分離）。
- **Composite:** 用於表示部分-整體層次結構。確保客戶端可以通過共同的 `Component` 接口統一對待單個物件和物件組合。
- **Decorator:** 用於動態地為物件附加額外責任。優先使用此方法而非子類化來擴展功能，以防止類爆炸。確保裝飾器具有與其裝飾的組件完全相同的接口。
- **Facade:** 用於為複雜子系統提供簡單、統一的接口。
- **Flyweight:** 用於通過與相似物件共享盡可能多的資源來最小化記憶體使用或計算開銷。
- **Proxy:** 用於為另一個物件提供代理或佔位符，以控制對其的訪問（例如，延遲加載、訪問控制或遠程通信）。

## Behavioral Patterns Guidelines 行為型模式指南

在產生涉及算法、控制流程或物件之間通信的程式碼時，應用下列模式：

- **Strategy:** 用於定義一組算法，封裝每個算法，並使它們可互換。通過委派給策略物件來消除選擇行為的複雜條件邏輯（`switch`/`if-else`）。
- **Observer:** 用於定義一對多依賴關係，其中一個物件（主題）的變化會自動通知並更新其他物件（觀察者）。保持主題和觀察者之間的鬆耦合。
- **Command:** 用於將請求封裝為物件。這對於實現撤銷/重做功能、隊列或請求日誌記錄至關重要。
- **State:** 當物件的行為高度依賴於其內部狀態，並且必須在運行時改變其行為時使用。將每個狀態表示為單獨的類。
- **Template Method:** 用於在基類中定義算法的骨架，將具體步驟延遲到子類，而不改變算法的結構。
- **Chain of Responsibility:** 用於將請求沿著潛在處理者的鏈傳遞，直到有一個處理它，避免將發送者與特定接收者耦合。
- **Mediator:** 用於集中管理一組物件之間的複雜通信和控制邏輯，避免它們彼此直接引用。
- **Iterator:** 用於提供一種標準方式來順序訪問聚合物件的元素，而不暴露其底層表示。
- **Visitor:** 用於在不改變元素類的情況下，對物件結構定義新的操作。這對於在穩定的組合結構（如抽象語法樹）上執行不同的分析非常有效。
- **Memento:** 用於在不違反封裝的情況下捕獲和外部化物件的內部狀態，允許稍後恢復物件（對於複雜的撤銷機制非常有用）。

## Copilot 的程式碼生成規則

- **Pattern Recognition:** 當被要求解決一個與 Go​F 模式相對應的問題時（例如，「我需要一種方法來撤銷此操作」、「我有多種計算稅款的方法」），請在註釋中明確提及您正在應用的模式。
- **Interface First:** 先生成介面或抽象基類，再生成具體實現。
- **Immutability & Encapsulation:** 預設將欄位設為 `private`。僅在必要時提供 getter/setter。偏好不可變物件。
- **Naming Conventions:** 在類名中使用模式名稱以增進理解（例如，`TaxCalculationStrategy`、`ButtonDecorator`、`WidgetFactory`），但在適當時保持名稱與領域自然對應。
- **Avoid God Classes:** 將大型、複雜的類拆分為較小、專注的類，通過 Mediator 協調或由較小的 Strategy 物件組成。
- **Single Responsibility Principle:** 確保每個類只有一個變更的理由。如果一個類做得太多，將其重構為多個類。
- **Open/Closed Principle:** 設計類時應對擴展開放，對修改封閉。使用抽象類或介面允許在不更改現有代碼的情況下添加新行為。
- **Liskov Substitution Principle:** 確保子類可以替代其基類而不改變程式的正確性。避免違反此原則，確保派生類不會加強前置條件或削弱後置條件。
- **Interface Segregation Principle:** 偏好多個專用介面而非單一通用介面。客戶端不應被迫依賴它們不使用的介面。
- **Dependency Inversion Principle:** 依賴抽象，而非具體實現。高層模組不應依賴低層模組；兩者都應依賴抽象。
- **Use Design Patterns Judiciously:** 當設計模式能解決代碼庫中的實際問題時再使用。避免過度設計，僅在模式能在可維護性、靈活性或可讀性方面提供明顯好處時使用。
- **Document Intent:** 使用設計模式時，包含註釋說明為何選擇該模式以及如何應用。這有助於未來的維護者理解設計決策的理由。
- **Testability:** 確保生成的代碼可測試。使用有助於單元測試的模式（例如，依賴注入以便於模擬）。編寫測試以驗證所使用模式的行為。
- **Refactor Iteratively:** 在重構現有代碼以應用設計模式時，採取迭代方式。從小的、漸進的變更開始，改善設計而不引入錯誤。使用測試驗證在重構過程中行為保持正確。
- **Performance Considerations:** 注意設計模式的性能影響。一些模式可能引入額外的抽象層，影響性能。使用分析工具識別瓶頸，並在不犧牲可維護性的前提下進行優化。
- **Consistency:** 在整個代碼庫中一致地應用設計模式。如果在代碼的某部分使用了特定模式，考慮在類似情況下也使用它，以保持一致的設計語言。
- **Review and Iterate:** 定期審查代碼庫，尋找應用設計模式或重構現有代碼以更好地遵循 OOP 原則的機會。鼓勵專注於設計質量和遵循這些指南的代碼審查。
- **Stay Updated:** 跟上 OOP 設計模式和最佳實踐的最新發展。持續學習並調整您的編碼風格，以納入新的見解和技術，從而提高代碼庫的質量。
- **Balance Simplicity and Flexibility:** 雖然設計模式可以提供強大的解決方案，但它們也可能增加複雜性。在簡單性和靈活性之間尋求平衡，確保代碼保持易於理解和維護，同時仍能適應未來的變化。當問題可以通過簡單函數解決時，優先使用函數定義；當類和模式提供明確的組織性好處時，使用類和模式。
- **Use Repositories and Typing definitions:** 在生成涉及複雜數據結構或交互的代碼時，考慮使用存儲庫來抽象數據訪問，並使用類型定義以確保代碼庫中的類型安全和清晰性。這有助於保持關注點的清晰分離，並提高代碼的整體可維護性。

## Logging and Error Handling 日誌記錄和錯誤處理

- 套用設計模式時，請確保日誌記錄和錯誤處理得到適當整合。
- 故障安全、響亮、清晰、及時。
- 避免靜默失敗，確保錯誤記錄具有足夠的上下文，以便於調試和維護。
- 在適當的情況下使用自定義異常，以提供更有意義的錯誤信息，並允許在客戶端代碼中進行更細粒度的錯誤處理。
- 明智地使用異常塊，確保它們用於處理預期的錯誤情況，而不是控制正常的程序流程。
- 使用日誌框架來管理日誌級別和輸出，從而更好地控制不同環境（例如開發與生產）中的日誌行為。
- 在每個類和函數中適當使用 info、debug、warning、error 和 critical 日誌級別，以提供對應用程序行為和潛在問題的清晰洞察。考慮實施集中式錯誤處理機制（例如全局異常處理器），以確保整個應用程序中的錯誤響應和日誌記錄一致。

## Documentation 文檔

- 套用設計模式時，確保代碼有良好的文檔。
- 使用英文的 docstring 來解釋類和方法的用途，並包括註釋以澄清複雜的邏輯或設計決策。除非現有代碼中使用了其他模式，否則使用 numpy 模式來記錄 docstring 中的參數和返回值。在首次使用此指令時，詢問開發人員他偏好的 docstring 參數和返回值類型，並在此處覆蓋 numpy docstring 定義，對所有後續的編程任務使用這種 docstring。這有助於其他開發人員理解代碼的意圖以及如何有效地使用它。
- 考慮使用 Sphinx 或 JSDoc 等工具從代碼庫生成文檔，使開發人員更容易導航和理解可用的類、方法及其預期用法。
- 此外，在 README 或專用文檔文件中維護高級架構概述，說明不同組件和模式如何在整體系統架構中協同工作。
- 將文檔分為用戶文檔（如何使用代碼）和開發者文檔（代碼如何工作以及如何維護）。確保隨著代碼的演變，這兩種類型的文檔都保持最新。
- 在適當的情況下使用圖表（例如 UML）直觀地表示類和模式之間的關係，幫助對 OOP 設計模式不熟悉的開發人員理解。
- 鼓勵開發團隊內部形成文檔文化，強調其對維護乾淨且可維護的代碼庫的重要性。
- 避免通過不斷創建包含相同內容的新文檔文件來爆炸式增加文檔。
- 掃描現有的文檔文件，以擴展它們或以相同風格構建新的所需文檔。保持簡潔、清晰，並專注於代碼及其設計模式的最重要方面。
- 避免冗餘或過於冗長的文檔，這可能會使開發人員不堪重負，並掩蓋他們理解代碼庫所需的關鍵信息。
